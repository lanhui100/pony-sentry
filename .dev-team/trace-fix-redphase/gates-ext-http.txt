## 偏离与说明（须知会 Lead）

1. **`_` 前缀未知字段一律丢弃**（契约 v1.5-3 原文「以 `_` 开头的键不特殊处理」存在两种读法）：
   我按「服务端保留命名空间」处理——否则客户端可伪造 `_redactions`/`_warnings` 覆盖服务端派生事实。
   若契约本意是「原样保留在顶层」，改一行即可（`if !key.starts_with('_')` → 恒定成立），但需同时接受伪造风险。
2. **`_redactions` 在脱敏之后注入**：保证计数本身不被二次扫描改写；`_unmapped`/**`_warnings` 在脱敏之前注入**，
   使未知字段里的密钥同样被计入与替换（实测 `secrets:1` 来自 `_unmapped` 之外的 `token` 键，行为正确）。
3. **`trace_payload_bytes_total` 用「持久化行 payload 序列化长度」**（Lead 指定口径），**不是**请求体长度；
   重复上报同一 session 会按持久化后的聚合体积再累加一次（counter 语义 = 每次 ingest 观测到的体积）。
4. **`merge_lost`/`truncated` 直接读 core getter**（`trace_merge_lost_total()` / `trace_truncated_total()`），
   不在 server 侧再存一份，避免同一事实两个家；代价是 `/metrics` 依赖 core 进程级静态量（同进程，无跨进程问题）。
5. **`?order` 与 `?fields` 非法值 → 400**（与 `eval_status`/`limit` 的既有严格风格一致）；缺省/`reported_at`/`full`
   分别等价契约默认。
6. **webhook 未配置时零副作用**：不建 client、不建 task、不建去重表条目；`TRACE_WEBHOOK_URL=""` 视作未配置。
7. **webhook 与全链路一致性**：投递失败只 `warn!`；`claim()` 在**投递前**登记，故 10 分钟内失败也不会重试（符合契约「不重试」）。
8. **`crates/server/tests/pg_api_duplicate_test.rs` 1 行补齐**：`AppState` 新增 `notifier` 字段的编译必要改动（无断言变化）。

## 残余风险 / 交接
1. **v1.5-6（`trace_turns.run_id` + `?run_id=` 双匹配）属 core 侧**；HTTP 侧仅透传 filter，未改语义。
2. **webhook 去重是进程内**：多副本部署时各副本各自去重（同一失败可能被 N 个副本各发一次）。如需全局去重需外部存储，属后续波次。
3. **`X-Total-Count` 每次列表多一次 `count_traces` 查询**；大表高 QPS 下建议加索引/缓存（已在 core 侧 `(run_id)/(turn_status)/(updated_at)` 索引面上）。
4. **`?fields=summary` 的 DTO 需与控制台同步演进**：新增列时两处都要改（本轮无新增列）。

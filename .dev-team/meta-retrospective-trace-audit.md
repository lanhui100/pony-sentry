# 元框架复盘：trace 采集质量审核（job_copilot cards 事故样本）

> 复盘对象是**协作元框架与组织协议本身**，不是被审业务代码。上一轮（wave-6）复盘见
> `.dev-team/meta-retrospective.md`；本轮为「只审核、不实施」的一次性审核战役。

## 1. 通信拓扑与信噪比（Topology & Noise）

- 名册：Lead（编排+基线+裁决+汇总）→ protocol-scribe（27 判据 + 39 字段矩阵）→ auditor-core（消费者 18 条）→
  auditor-diagnostic（诊断八问 + 生产者语义 + 13 条建议）→ verifier（59 条独立裁决 + 4 条新发现）→
  Subagent 池 3 路 Explorer（pony-sentry 管线 / 生产者契约 / 文档契约）+ 2 路 L3 审查。常驻 4 ≤ 8，审查不占槽位。
- 信噪比最高的是**verifier 的独立复现**：T2 报「19/20 丢轮」，verifier 自跑得 18/20，并顺带发现 4 条双方都漏的
  缺陷（幻影 id、响应 total 双真值、负数分页 500、脱敏绕过）——独立分权制在本轮直接产出了增量事实。
- 信噪比第二高的是**L3-B 的隐私/容量视角**：它用两个实验（extra 置 null、2.4MB 合并行）推翻了报告两条主推建议，
  证明「对抗审查不写代码也能改变结论方向」。
- 噪声与浪费：① Explorer 三份地图共 ~120 行，其中文档面约 60% 信息在成稿前即被判定为「背景」而未入报告——
  下一次应在 Explorer prompt 里直接限定「只取将被引用的路径:行号」；② L3-A 首轮与 Lead 的 send_message 竞态
  （子代理已结束但 target 失效），导致重复派发一次 L3-A/L3-B，多花约 10 分钟与一次上下文重建。
- 令牌产出比：最省的是把「覆盖率」做成可复算的 8 问表（一次投入，verifier 与 L3-A 都能直接复核）；
  最贵的是报告草案先行、验证后到——草案 §9.3 留白被 L3-A 判 BLOCKER，属流程可预防项（见 §4 第 2 条）。

## 2. 门禁穿透与误杀率（Gate Penetration / False Negatives & Positives）

- 独立 Test Agent（verifier）有效封堵了「自证」：T2/T3 的 59 条结论被逐条以自跑 HTTP+DB 复核，0 条 REFUTED，
  但同时产出 4 条新缺陷与 10 条口径不一致——说明「不复核则口径漂移」是真实风险，而非形式主义。
- 误杀：Lead 的初版 P0 分级（W-01/W-02）被 L3-A 用**判据自身定义**（P0 = 直接阻断本次诊断）判为误用——
  门禁不是没拦住错误，而是**判据定义与分级实践脱节**，属协议层缺陷，已在报告 §0 与 §3 修正为 P1。
- 门禁穿透：报告草案未等 verifier 完成即成型，导致 L3-A 审到的是「未并入验证结果」的旧版（BLOCKER ①）。
  这是**时序门禁**缺失：应在冻结的契约里写「报告草案不得早于 verifier 裁决落盘」。
- 实验卫生：3 名成员并发写同一个 Postgres，发生一次「通配删除他人 probe 行」事故（auditor-core 误删 2 行），
  并被 verifier 的在飞实验放大。事后用「唯一前缀 + 精确删除 + 删除前后 count」三件套收敛，终态 0 残留。
  这说明**共享库的写域隔离不能只靠口头约定**，需要机械前缀规范（本轮已补入简报 §9，但未回写到团队模板）。

## 3. 分工契约与隔离有效性（Contract Isolation）

- 信息下发克制：T2 只拿到消费者路径与判据，T3 只拿到诊断问题与生产者路径，两者未互相污染；verifier 只拿到判据与收据，
  不拿结论推导过程——因此它的 4 条新发现是独立产生的。
- 滚动契约账本有效：简报（00-brief）冻结目标/非目标/证据标准/访问收据/实验前缀，5 个成员零返工地对齐；
  唯一冲突（observability_store 不是 trace 生产者）由 protocol-scribe 主动改锚并回报，未造成结论污染。
- 波次并行：T1→(T2∥T3)→T4 的 DAG 成立，T2/T3 各自 18/41 条结论在 15 分钟内并行产出；
  T4 因 blocked_by 不能提前认领，但被允许先做独立收据——这是「阻塞依赖 + 预取」的有效折中。
- 缺口：审查产物（L3-A/L3-B）在冻结契约里没有 write_scope 预登记，导致两次 L3-B 并发写同一 JSON 文件、
  后者追加未覆盖前者（侥幸无损）。下轮应为每个审查者预分配独立文件名。

## 4. 元协议迭代建议（Self-Evolving Protocol）

1. **报告类任务的时序门禁**：凡「审核/评估」型交付，把「独立验证裁决已落盘」写进报告草案的 blocked_by，
   禁止先成稿后回填（本轮 L3-A BLOCKER ① 的直接来源）。
2. **共享外部存储的写卫生规范化**：实验前缀必须含成员名+随机串，删除必须精确匹配自身前缀，
   收据必须含删除前后 count；违规一次即在本波次 state.json 记 `hygiene_violation`。
3. **P0/P1 分级必须引用判据原文**：分级结论旁强制写一句「按 <判据 ID> 的定义」，避免 L3-A 指出的
   「判据说 A、分级做 B」的静默漂移。
4. **审查者文件名预分配**：`60-review/review-<role>-<round>.json`，在任务板 write_scopes 登记，
   禁止两个审查实例写同一路径。
5. **Explorer prompt 收口**：要求首行输出 `will-be-cited: <path:line 列表>`，否则摘要不得进入 Lead 上下文，
   以压低「读了 60% 不会用」的 token 损耗。

## 5. 追加轮：外部基准复核（DSH）的元观察

- 触发：用户要求「参考 dsh 源码的 trace 实现验证本次审核」。Lead 派 2 名只读 Explorer 扫 `packages/telemetry`、
  `packages/core/session`、`packages/session/*`、`packages/llm/llm*`，再以「27 条 finding × DSH 事实」矩阵复核。
- 结果：0 条被反驳、17 条被印证、8 条实现方式需修正、3 条不可比。**最有价值的不是印证，而是三处修正**：
  ① `error_type` 不应闭集收敛（DSH 事故复盘把「用通用类覆盖结构化失败」列为归因反模式）；
  ② 采样应「不采样或自描述」，而非默认补元数据；③ 容量治理要有去重键与行级上限。
- 元教训：**内部对抗审查（L3-A/B）能查出自洽性与合规问题，查不出「行业成熟形态长什么样」**。
  外部基准是第三种独立性来源，成本低（2 个只读侦察 + 1 次矩阵对账），但能直接改写建议方向。
  建议写入 dev-team 元协议：涉及「可观测/契约/存储模型」类审核，**外部同类实现对照应作为标准第三路**。
- 执行瑕疵：第二名 Explorer（session-log/UI 方向）超时未回，其问题域由 Lead 亲自定点复核覆盖（session.md、
  session-telemetry.md、session-persistence-jsonl、otel session-log.ts），未阻塞交付；下次应在派发时给出硬时限与
  「先回已有事实再补细节」的分段回报要求。
